## Owner-controlled signing

Generate a key locally, with interactive passwords (not a command-line password):

```bash
keytool -genkeypair -v -keystore /secure/path/appbreak-release.jks -alias appbreak -keyalg RSA -keysize 4096 -validity 10000
```

Write untracked `android/key.properties` with these keys and your own values:

```properties
storeFile=/secure/path/appbreak-release.jks
storePassword=YOUR_PRIVATE_PASSWORD
keyAlias=appbreak
keyPassword=YOUR_PRIVATE_PASSWORD
```

Protect this file and retain encrypted offline copies of the keystore/password. Do not send secrets in chat. The Gradle release build uses owner signing only when that file exists; it does not silently use debug signing.

```bash
flutter pub get --enforce-lockfile
```

Output filenames should be checked against the actual build output. Do not claim signing unless `apksigner verify` passes. For F-Droid, coordinate signing/update compatibility with their build/signing process; a locally signed APK is not automatically accepted by F-Droid.

## F-Droid gate

F-Droid's current policy permits official Flutter SDK prebuilts subject to its rules; it still requires a public, properly licensed and buildable source project, compatible dependencies and reviewer approval. Submit only a build-verified, hardware-tested source release.

After device acceptance:

1. Commit complete source, lockfile, public metadata, screenshots and changelog.
2. Pin a verified Flutter commit/archive checksum and Gradle distribution checksum; upgrade the older test baseline and re-run tests if required.
3. Generate a complete source/dependency licence inventory for the actual release.
4. Confirm the FOSS release dependency graph excludes proprietary components at build time.
5. Prepare fdroiddata metadata using the actual immutable tag/commit and upstream source URL. Use the F-Droid Flutter recipe appropriate to their current toolchain. Do not invent a commit hash or publishable metadata before this exists.
6. Test the documented source build in a clean environment; address any scanner findings.
7. Submit for F-Droid review. Acceptance remains their decision.

The two Gradle flavors currently have the same functional code and no billing. Future store SDKs must use `playImplementation` and Play-only source sets. Baseline accessibility, notes, export and backup access stay available in every edition.
